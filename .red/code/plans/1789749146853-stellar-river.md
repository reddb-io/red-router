# Port: tudo o que PentatonicDev/9router implementou → red-router

## Objetivo

Portar **todos os 36 commits divergentes do fork** PentatonicDev/9router para o `main` do red-router, **exceto os 4 commits de CI específicos do repositório do fork** (f3f91de7, 1d01b22b, 191d91f4, 23da6257 — workflows noturnos de sync/docker/gitbook que apagariam nossos próprios workflows; decisão tomada e declarada abaixo). Estratégia: cherry-pick em ordem cronológica por fase (nosso `main` e o fork divergem do **mesmo** base `17c4cc76` — upstream decolua/9router não se moveu —, então os picks aplicam quase limpos), com gate de testes/regressão ao fim de cada fase.

## Contexto verificado (fatos, não suposições)

- Fork clonado em **`/tmp/redcode/9router-fork`**, com remote `upstream` já apontando para decolua/9router. 36 commits no-merges em `upstream/master..HEAD`; base comum `17c4cc76` ("feat(claude-code): drive auto-compact window…") é **ancestral do nosso main** (verificado via `git merge-base --is-ancestor`).
- Divergência nossa vs base nos caminhos que o fork toca é pequena: `src/lib/db`+`src/lib/auth`+`src/sse`+`open-sse` = 33 arquivos, +323/−73. `src/lib/db/schema.js`, `repos/*` e `migrations/` são **idênticos ao base** (só `settingsRepo.js` ±2). Conflito esperado: `open-sse/utils/sessionManager.js`, alguns translators, `src/sse/handlers/chat.js` (±44 linhas), `EndpointPageClient`/dashboard (limpeza 9English/9Remote já feita por nós — o pick de f2922025 também mexe lá; manter NOSSO estado).
- Temos provider **openrouter** no registry (`open-sse/providers/registry/*openrouter*`) e menção em `open-sse/config/ttsModels.js` — o trio openrouter do fork é aplicável.
- `src/instrumentation.js` **existe** no nosso repo (o pick 873fe72a que move refresh de token para o boot aplica sobre ele).
- `package.json` sem `kysely`/`pg`; `.changeset/` existe (config.json); histórico recente usa changesets + Conventional Commits via PRs.
- Últimos pedidos das últimas 8h (outras sessions) — **já mergeados no main** (PRs #6–#11, hoje 08:13–13:10): standalone boot fixes (#6,#7), service mode systemd/launchd (#8), data dir `~/.red/router` + import de `~/.red-router`/origem 9router oficial (#9), limpeza dashboard 9English/9Remote + versão runtime + update-check (#10), tray icon marca RedDB (#11). O erro "failed to send prompt / no schema with key or ref …draft/2020-1/schema" é bug do harness Redcode (cliente), **fora do escopo deste repo**. O port deve **não regredir** nada disso (data dir e port 25050 são nossos e permanecem).

## Decisões

1. **Excluir os 4 commits de CI do fork** (só fazem sentido no repo dele; no nosso apagariam workflows próprios). Explicitamente fora do escopo.
2. **Cherry-pick com `-x`** por commit (preserva referência upstream na mensagem); conflitos resolvidos mantendo nosso branding (`25050`, `~/.red/router`, red-router) e a limpeza de dashboard já feita.
3. **Ordem cronológica do fork** dentro de cada fase — preserva as dependências reais (ex.: contrato de erro `9af01874` precede `f79fc65f` que cita o 503 `no_active_credentials`; keys/auth precedem Postgres `69efa979` que converte os repos criados por elas).
4. **Sempre pnpm** (instrução global do usuário). Commits Conventional; changeset no fim; **sem PR** (usuário não pediu — commits diretos na branch de integração; merge em main no fim).
5. `SCHEMA_VERSION` termina em **5** (1→2 keys, →3/4 owner, →5 já no estado do fork); migrations entram pelos picks — nosso migrations/ é idêntico ao base, risco baixo.
